# 自主拟人社交插件

一个为 AstrBot 设计的主动社交插件，让 AI 不再只能被动等待用户发送消息，而是能够根据互动情况、时间间隔、待跟进的话题和自身状态，判断什么时候适合主动联系对方。

**核心定位**：插件负责主动社交的时机、对象和行为管理，由大模型结合角色人设与聊天上下文，判断是否开口并生成具体内容。

它并不是一个简单的定时消息发送器，而是一套围绕主动聊天、话题延续和交流节奏设计的社交机制。

## 一、主要功能

### 1. 主动发起聊天

插件会在后台周期性检查当前的社交状态，判断是否存在适合主动联系的对象。

它不会每次检查都发送消息，也不是给每个用户设置固定的发送时间。插件会逐步积累主动交流的念头，并结合关系、近期互动、冷却时间、角色状态和其他限制，决定是否进入发送流程。

主动消息可以是自然的问候、分享、对某个人的关心，或者根据近期聊天内容开启的新话题。具体表达由大模型结合角色人设生成，而不是从一组固定问候语中机械挑选。

### 2. 话题延续与未完事项回访

插件不只负责开启新话题，也可以尝试把之前的交流继续下去。

主要包括：

- **未完话题接续**：双方刚才聊到一半，之后可以根据情况继续交流。
- **回应追问**：对方之前提到一件事情，但没有说完或没有给出结果，插件可以在合适的时间询问后续。
- **时间锚点回访**：用户提到稍后要做某件事、准备某项活动等，相关线索可以成为以后重新联系的理由。
- **沉默后的接话**：对话暂时中断后，插件可以判断是否适合自然地接上一句，而不必每次都重新打招呼。
- **主动收场**：主动发送的消息长时间没有得到回应时，可以在适当条件下结束这一轮交流，而不是一直追着对方发送消息。

这些行为有各自的触发条件和间隔限制，不会因为存在一条历史话题，就无限次重复同一件事。

### 3. 根据互动调整交流节奏

插件会区分不同用户的互动情况，并根据已有的关系与交流记录调整主动联系的节奏。

例如，刚刚聊完的人通常不需要立刻收到一条新的、无关的话题；长时间没有联系的人，则可能在合适的时候重新收到消息。

插件提供多层限制，包括：

- **个人冷却时间**：避免短时间内反复联系同一个人。
- **安静时段**：在设置的休息时段内限制主动发送。
- **消息频率限制**：控制每轮、每小时以及不同用户之间的发送数量。
- **重复内容检查**：减少同一个角色在短时间内向多名用户发送高度相似的内容。
- **模型判断**：启用相应配置后，在发送前让模型判断这条消息现在是否合适。模型可以选择不发送。
- **失败保护**：模型或平台发送失败时，不应把失败当成一次成功的交流。

这些规则的目的是让主动聊天更有选择性，而不是单纯提高发送数量。

### 4. 用户选择与个性化互动

插件会参考用户的近期互动、关系情况、未完话题和主动联系记录，选择合适的交流对象。

它还支持从 AstrBot 已有的聊天历史中导入符合条件的私聊对象，让插件不必只认识安装之后才开始交流的人。

也可以通过配置指定额外的候选用户。

用户选择并非简单按照最后发言时间排序。插件需要结合当前是否适合联系、此前是否已经联系过，以及是否存在值得继续的话题进行判断。

### 5. 群聊互动

除了主动私聊，插件也提供可配置的群聊互动能力。

主要包括：

- **群聊心流**：机器人在群里参与交流后，可以在特定关注窗口内判断是否适合继续接话。
- **主动破冰 / 起话头**：群聊长时间安静时，或者她在群里静了一阵时，可以主动发起轻量的话题。
- **发言风格参考**：在启用相关功能时，收集群聊中的部分发言作为风格参考，辅助生成更符合群聊环境的内容。
- **群聊频率控制**：限制连续插话次数、相邻消息间隔和每小时的互动数量。
- **不点名、说自己的生活**：主动开口是对着整个群说的，默认不叫任何群友的名字；话头优先分享她自己刚做完/正在做/想去/还没做完/梦到的具体小事，而不是只有天气。
- **没话说就不发**：破冰/起话头也会先判断（SEND/NO），没有一件真值得分享的事就这次不发，不硬凑。

群聊行为具有独立的开关和限制。可以根据实际需要启用或关闭，不必使用全部功能。

多台机器人位于同一个群时，可以设置触发条件，避免一条群消息同时触发多台机器人。

## 二、与人形化伴侣插件的关系

自主拟人社交插件既可以单独运行，也可以与人形化伴侣插件配合使用。

### 独立运行模式

没有安装人形化伴侣插件时，自主拟人社交插件仍然能够使用自己的状态、互动记录、念头积累和社交规则来决定是否主动联系用户。

这种模式适合只需要主动聊天功能的场景。

### 联动模式

安装人形化伴侣插件后，社交插件可以读取其提供的角色状态、时间和日程等信息，用来辅助判断主动交流的时机。

例如，角色当前精力不足时，可以降低主动联系的意愿；角色的生活背景与时间信息也可以作为生成主动消息的参考。

两者的职责保持分离：

| 对比 | 人形化伴侣插件 | 自主拟人社交插件 |
|---|---|---|
| 身体与情绪状态 | 负责维护 | 读取相关信息辅助决策 |
| 日程与生活背景 | 负责生成和维护 | 可作为主动交流的参考 |
| 主动联系用户 | 不负责 | 负责判断与执行 |
| 新话题与未完话题 | 提供部分状态背景 | 负责社交层的选择与跟进 |

联动属于可选能力，不要求必须安装人形化伴侣插件才能使用本插件。

## 三、可选的长期记忆联动

如果已安装兼容的记忆插件，例如「我会牢牢记住你」，可以启用相应的记忆桥接功能，让主动交流在生成前**按这次开口的由头**读取可用的长期记忆，并在发送后执行相应的记忆写回。

这可以帮助主动消息参考长期记忆，而不只依赖本插件保存的近期话题和状态。

没有安装记忆插件时，主动社交的基础功能仍然可以运行，只是无法使用这项额外的长期记忆能力。

记忆联动是可选功能，不是主动消息运行的必要条件。

## 四、主动消息是如何产生的？

一次主动交流通常会经历以下过程：

1. **检查状态**：查看插件是否启用、运行环境是否正常，以及是否需要进入下一轮判断。
2. **选择对象**：根据用户的互动情况、念头积累和相关限制选择候选对象。
3. **寻找交流理由**：判断是否存在问候、新话题、未完事项或其他适合联系的由头。
4. **检查发送时机**：考虑近期是否聊过、是否处于安静时段、是否触发冷却或频率限制。
5. **判断并生成消息**：启用模型判断时，允许模型拒绝不合适的主动消息；通过后，再根据上下文和角色人设生成内容。
6. **验证并发送**：检查生成结果，尝试通过当前平台发送消息。
7. **记录结果**：根据实际执行结果更新互动记录、发送状态和后续社交节奏。

这里的时间间隔主要决定插件何时进行检查，并不意味着每经过固定时间就一定会发送消息。

## 五、常用指令

| 指令 | 作用 |
|---|---|
| `/自主社交状态` | 查看念头积累、社交节奏、Core 联动及相关运行状态 |
| `/触发社交` | 手动触发一次主动社交流程，便于检查当前功能 |
| `/主动消息记录 [用户ID]` | 查看主动消息记录 |
| `/群社交状态` | 查看群聊心流的运行情况 |

其中，管理指令受插件的权限配置控制。执行手动触发前，插件也会检查基本运行条件；如果模型正处于失败退避或引擎不可用等状态，会说明原因，而不是直接消耗社交状态。

## 六、配置建议

插件提供较多进阶配置，但初次使用时通常只需要关注以下几项：

| 配置 | 作用 |
|---|---|
| `mode` | 选择自动联动或独立运行模式 |
| `activity_level` | 调整整体主动交流的积极程度 |
| `urge_refill_hours` | 调整主动联系的念头积累速度 |
| `recent_talk_minutes` | 设置刚聊完之后，不另起新话题的时间范围 |
| `quiet_start` / `quiet_end` | 设置主动消息的安静时段 |
| `heartbeat_min_minutes` / `heartbeat_max_minutes` | 设置后台检查的时间间隔 |

其他配置用于控制未完话题跟进、群聊互动、发送上限、历史导入和数据保留等行为。建议先使用默认配置，确认运行正常后，再按实际需要调整。

需要注意，后台检查存在时间间隔，因此分钟级条件的实际触发时间可能晚于配置值。这是检查周期带来的正常现象，不代表每到配置时间就会立即发送消息。

## 七、数据与隐私

插件会保存主动社交所需的状态、用户互动记录和话题信息，以便后续决策能够参考此前的交流。

部分配置允许保存聊天正文，用于话题延续与消息生成。启用历史导入后，插件还会读取 AstrBot 中符合条件的历史私聊记录。长期不活跃用户的数据可以按保留期限清理。

使用前建议检查以下配置：

- `store_message_text`：是否保存聊天正文。
- `user_retention_days`：长期不活跃用户的数据保留期限。
- `history_ingest`：是否从已有的 AstrBot 会话记录导入用户。
- `memory_bridge_enabled`：是否启用兼容记忆插件的联动。

如果不需要相关能力，可以关闭对应功能。历史导入、正文保存与长期记忆联动是不同的机制，应分别根据需要设置。

## 八、运行条件与兼容性

插件面向 AstrBot 4.x 环境，支持独立运行及与人形化伴侣插件联动。

主动消息能否成功送达，还取决于当前平台是否支持相应的主动发送能力，以及模型和平台服务是否正常。即使插件已经判断应当联系某位用户，也不代表所有平台都一定能够完成发送。

如果发现插件一直不主动联系用户，可以先通过 `/自主社交状态` 查看插件是否启用、候选对象是否符合条件、念头是否积累完成，以及模型、冷却、时间限制和平台发送是否存在阻碍。

## 总结

自主拟人社交插件的重点不是定时发消息，而是让 AI 有机会主动开启交流、延续未完的话题，并在适当的时间重新联系用户。

它将对象选择、主动意愿、话题跟进、模型生成和发送限制结合起来，在主动性与打扰控制之间取得平衡。

人形化伴侣插件负责角色的生活与状态，自主拟人社交插件负责角色什么时候主动开口。两者既可以独立使用，也可以组合使用。

## 它解决什么问题

让 bot 在**没有收到消息的时候**也主动找熟人说话，而且说得像个有自己生活的人，不像一个定时器。

主动开口其实是几件不同的事，本插件把它们走成几条互不依赖的路：

| | 什么时候开口 | 靠什么 |
|---|---|---|
| **她这边刚发生一件事** | **立刻**：刚做完、正在做、梦到、天气变了 | 由头的**有效期**（2~3 小时，过期不补发） |
| **对方那边有动静** | 想起就问：TA 提过的事、说过的锚点 | 由头的有效期（1 天） |
| **没事干，问候一句** | **隔了多久就多久**，不绑日历 | 静音时长 + 关系档的最小间隔 |
| **有一件具体的事才开口** | 慢慢来：念头只管节奏，不管发不发 | `urge_refill_hours`、`activity_level`、`min_gap_minutes` |
| **追问那件事** | 几分钟：对方回得越来越敷衍 | `probe_after_minutes`（不看念头） |
| **问一句在不在** | 十几分钟：话说到一半人没了 | `followup_after_minutes`（不看念头） |
| **回访没结果的事** | 几小时到一夜：你提过一句没说后来 | `loop_min_hours` / `loop_max_hours` |
| **给悬着的话收场** | 几小时到几天：她主动发的没人接 | `closer_after_hours`（最多收三次） |

### 她那边发生的事，和你有关的事

Core 的日程是**角色级**的——她今天「刚忙完个案笔记」这件事，同一个 bot 下的所有人
都读同一行。所以纯粹拿它当由头，会 1 小时 41 分内给 12 个不同的人发同一句。

现在的做法是两道：

- **跨用户撞车护栏**：和近 2 小时内**发给别人**的消息太像就不发（`cross_user_repeat_ratio`）
- **提示词先摆素材**：把 TA 说过的话和她刚发生的事一起给模型，让「想什么」成为
  对素材的自然反应——同一件事，不同的人会接出不同的话

### 关系分三档：看的是这段关系有多热

**不按好感度绝对值分档。** 有运营为了让用户更好攻略，会把初始好感度设成 40 之类；
聊久了直接飙到 80。只看绝对值的话，那种人和「一直停在 80 但从不回话」的人是同一档——
而该被多找的恰恰是前者。

所以看的是**关系涨幅**（现在的好感 − Core 的基线）、近期互动量、回复率、认识时长。
好感度在里头只作参考。

| 档 | 最小间隔 | 什么时候 |
|---|---|---|
| 高 | 20 分钟 | 关系很热，一天能发好几次 |
| 中 | `min_gap_minutes`（默认 1 小时） | 算熟 |
| 低 | 12 小时 | 没什么来往。连着两次发不出去就**停发**，等对方先开口 |

一轮里能从当下状态派生出来的由头，实测**最多 3 条**（三档都是），因为能派生的
素材就那么几处：刚做完的、正在做的、接下来那件、想做的、还没做完的、梦到的，
天气只是「真变了」时的备选。所以「一天能发几次」取决于**一天里触发多少轮**，
不取决于池子有多大。

**「由头池」那一列说的是**读取侧一次最多取几条**，不是能存几条。
实际上由头是**一次性队列**：一条用完就让位，下一轮从当下状态重新派生。
所以真正决定一天能发几条的是关系档的最小间隔和当天的由头供给，不是这个数。

**高好感不设日上限。** 一天能发几次取决于她当天有几件事发生——那该由她的生活决定，
不是由人拍的节拍器决定。防扎堆靠另外三道：低档压根没由头可挑、同一件事一辈子只说一次、
模型自己否决。

模型对**谁都**有否决权，好感高也不例外：好感高只是让开口更自然，不是非发不可。
否决和「验收拦下」分开记账——前者不消耗由头（这个人此刻不该被找），后者消耗
（这句话她驾驭不了）。

### 开口必须有一个「由头」

**念头攒满了不代表要说话。** 念头只决定「有事由之后等多久发」，不决定「发不发」。

每一次主动消息都要携带一件具体的事（由头），来源六选一：兑现自己答应过的、
对方的时间锚点到期了、对方提过还没下文、话说到一半断了、到了问候窗口、
或者从她自己的状态里刚派生出来的一件（「刚忙完方案」「外面在下雨」）。

- **真实**：全部由插件已持有的数据派生，不让模型现编
- **一次性**：用过的进冷却 7 天，同一件事一辈子只出现一次
- 派不出由头 → **这轮就不说**。一个 bot 不该每天对一百多个陌生人找话说

### 两条通道，不是一套闸门

| 通道 | 受「刚聊过」约束吗 | 说什么 |
|---|---|---|
| **接续型** | 是（别打断） | 到点的由头、追问、回访、兑现承诺、收场 |
| **念想型** | **否** | 没有正事，就是想 TA：问 TA 在干嘛、惦记 TA 说过的话 |

**为什么分开**：对方每发一条消息，念头就清零；念头要攒四五个小时才够门槛。
所以对方聊得越勤，她越永远攒不起来——仿真里好感度同样 0.75 的两个人，
对方从不回复的 7 天被主动找 20 次，对方每小时发一句的**一次都没有**。
于是「刚聊过」对「想你了」是错的：过了一阵子想起你，不是在打断谁的对话。
拆开之后，**好感高的人从此是最容易被主动联系的人**。

念想类额外要求正文里必须有第二人称（验收层会拦）——「你今天忙到几点啊」，
而不是「我今天有点累」。冷落两次以上只留早安，四次以上完全不问。

> 每个用户**独立计算**：A 被找过不会让 B 多等。每个人自己的念头与
> `user_cooldown_minutes` 才是节奏来源；`max_sends_per_round` 只是别在一轮心跳里
> 把话一口气全倒出去的护栏。

## 群聊心流

上面那些都是**私聊**主动。群聊侧几条路由 `group_*` 开关控制，与 `private_only` 互不影响：

| | 什么时候 | 靠什么 |
|---|---|---|
| **心流接话** | bot 在群里说过话后的关注窗口内，群里继续聊 | `group_flow_enabled`、`flow_window_minutes`（无 @，模型可拒答） |
| **冷场破冰** | 群安静超过几小时 | `group_icebreak_enabled`、`group_idle_hours`（没话说可不发） |
| **主动起话头** | 她在群里静了一阵 | `group_topic_enabled`、`group_topic_gap_hours`（没话说可不发） |
| **发言参考库** | 生成时注入「这个群怎么说话」 | `group_ref_lib_enabled`、`group_ref_prompt_count` |

> **保守档**：心流只在 bot 自己刚发过言后的窗口内才可能无 @ 接话，不主动盯整个群。
> **不刷屏**：两次插话最短间隔、每窗口上限、每群每小时总上限、连着没人接就安静，四道闸叠着拦。
> **安静时段对群聊同样生效**：深夜群里有动静她也不会插话（这一点曾经漏掉过，已修）。
> **只接没人点名的话（@ 的部分）**：① 被 @ 的消息交给主链路正经回复，心流不跟着插一句；
> ② @ 了别人的消息（哪怕不是本 bot）也不掺和；③ 群里另一台装了同样插件的 bot 发言，
> 也不会被当成「群友在说话」去接。
> **别人对聊可以插，由模型判断**（v1.28.0）：群里两个人在来回聊、或者这句话是在叫别人时，
> 插件不再硬拦，而是把语境交给模型——接得上、不打断才插；`group_interject_others` 关掉
> 则退回旧语义（这种场合一律不插）。频率/窗口等护栏照旧全部生效。
> **主动开口不点名**（v1.28.0）：破冰/起话头是对着整个群说的，一个名字都不给模型；
> 心流接话默认也不点名，只有 `group_mention_member` 打开时才允许叫**正在接的这一个人**
> 一句（起话头/破冰仍然不点名）。用户反馈的「主动消息发群时会叫别人」就是这条要治的。
> **话头是她自己的生活**（v1.28.0）：破冰/起话头的素材优先是她刚做完/正在做/今天想去/
> 还没做完/昨晚梦到的具体小事；节日、天气只是备选，天气还得「真的变了且 6 小时没说过」。
> 没有一件真值得分享的事时，模型可以答 NO——这次不发，也不占今天的额度。
> **接话也过验收**：心流接话与破冰跟私聊一样要过五道验收（动机泄漏 / 括号欠配 / 复读 / 协议残留 / 推情绪），
> 判不过就不发——宁可不接，不可发一条废话。
> **被踢就不再管**：心流只由实时群消息驱动；群发送失败隔离 24h；超 `group_stale_days`
> 天没见消息的群连样本一起清。用「群社交状态」指令（仅主人）看在管的群。
>
> ⚠ 默认在**所有群**启用，意味着心流接话是**公开可见**的；误判会当众发出。频率总闸与
> 保守触发是为了把打扰压到最低；不想要就把 `group_flow_enabled` / `group_icebreak_enabled` 关掉。

## 多台 bot 同群时（FAQ）

你如果有好几个 bot，且都在同一个群里，有件事要先说清楚：**每次只能靠 @ 来分家**。

### 一、「一个 `触发社交`，三四个 bot 同时动」

原因在 AstrBot 本身：群里一条不带 @ 的消息会送到**每一台** bot，多台又都装了本插件时，
它们就各自执行了一次「触发社交」。所以从 v1.27.4 起：

- **群里「触发社交」默认只认被 @ 的那台**（新开关 `trigger_group_requires_at`，默认开）。
  `@小夜 /触发社交` → 只触发小夜；@ 的是别人、或谁都没 @ → 其余几台静默跳过。
- 单台部署想保留「群里直接 `/触发社交` 不用 @」的旧习惯，把这个开关关掉即可。

### 二、「他不知道自己发过什么 / 把另一台 bot 当成我说的」

两个来源，都与 AstrBot 的 `platform_settings.ignore_bot_self_message`（面板：「忽略机器人自己的消息」）有关：

- **同类认不出**：多台 bot 同群时，**每台 bot 在事件层就是一个普通群成员**。本插件会把本进程
  见过的其它 bot 跳过（不当用户、不接它的话、不进风格库），含「只混群、从没私聊过」的那种；
  但**跨实例/跨容器的 bot 认不出**（各自一份状态）。
- **自己发过什么**：本插件对自己发出的消息是**发送侧记账**（不依赖平台把自消息回灌成事件），所以
  开不开那个开关，记帐都在。但如果你注意到「它把自己刚发的话当新消息 / 把别的 bot 的话当成你说的」，
  就去 AstrBot 配置里把 `ignore_bot_self_message` 打开（它会把自己发的消息在插件看到前丢掉）。

一句话：**多台 bot 同群时，聊天请 @ 明确的那一台**；不希望它们互相搭话，就别把多台都装本插件的 bot
放在同一个群里。

## 关于 Humanoid Core（可选依赖）

装了「Humanoid Core」插件时，插件会读它的状态并把它当**参考值**用：

| Core 给的 | 插件怎么用 |
|---|---|
| `body` 精力/社交能量/睡意/饥饿/困意 | 念头增速的油门与刹车；低于阈值时念头几乎涨不动 |
| `body.asleep` | 硬否决：日程写着她在睡就不发 |
| `routine` 生物钟夜 | **安静时段按这个判**，而不是插件配置里写死的 23 点（夜猫子人格凌晨四点睡，用 23 点判是错的） |
| `form.burst_ok` | 这一轮适不适合连着发 |
| `form.question_bias` | 偏低时提示「你这一轮不太想问句」 |
| `form.long_reply_ok` | 为 false 时把长度上限收到 40 字 |
| `form.max_chars` | 这一轮的单条字数上限 |
| `activity` / `day` / `weather` | 素材：她今天在干什么、刚做完什么、梦到什么、在哪、外面天气（天气只作备选，且要「变了」） |
| `feelings` | 身体感觉，出现在提示词里但要求「不要在消息里报告它们」 |
| `body.energy_text` | 直接用 Core 翻好的人话（"精神还不错"），不再两边各翻一遍同一个数字 |
| `user.nickname` | **她该怎么称呼这个人**——Core 从 TA 自报的昵称里认定，改口会跟着变 |
| `user.said` | 她自己记着对方说过什么（原话），作为素材进提示词，并注明别原样还回去 |
| `user.mood_tag` / `user.attention` | 对方此刻的状态标签、她有多在意这个人 |
| `persona` | 用来确认「两边演的是不是同一个人」，对不上时 `/自主社交状态` 会直接报出来 |

反过来，插件把「刚替谁主动开过口、被连着冷落几次」写回 Core 的 `humanoid_signals.json`，
Core 据此泄掉社交欲望、把冷落记进体感。两边各写各的文件，不存在并发写。
信号靠文件 mtime 判活（Core 那边 15 分钟过期），所以插件每轮心跳都会无条件重写一遍；
写不进去时 `/自主社交状态` 的「写回 Core」那一行会写明原因。

Core 的 `humanoid/wording.py` 里写着一句话，本插件现在也是这么做的：
**「这里不写台词也不写规矩，只描述状态」**。

> `mode=standalone` 表示完全不读 Core。`mode=auto`（默认）是有就读、没有就降级。
> 曾经还有一个 `mode=humanoid`（号称「强制要求 Core」），但代码里从来没有对应实现，
> 选它和 auto 行为完全一样——一个假装存在的档位比没有更误导人，已经删掉。
>
> **降级是可见的**：`/自主社交状态` 会明确列出当前读到了哪一层、哪些能力因为
> 读不到 Core 而停用了。不会再出现「装了个 Core，插件却像没装一样」而查不出原因。

## 功能

### 核心机制
- 念头（urge）惰性积分：只在被读到时按经过的时间补算，不为每个人挂定时器。
- 冷却项是**护栏**（防刷屏），不是节奏的来源。
- 安静时段与对方作息是硬闸：那个点就是不发，念头留着等合适的时候。
- LLM 同时负责「要不要说」和「说什么」；调度、积累、结算全在插件里。
- 播种：历史导入（读回装插件前就聊过的人）与播种名单（没聊过的人也能被主动找上）。

### 决策不会自相矛盾
- 引擎的闸门已经放行之后，提示词**不会**再劝模型「别发」——这两处曾是各说各话，
  导致每次到点都白烧一次 LLM 换一个「不说」。
- 模型必须按 `SEND`/`NO` 协议作答。**没按协议作答时本轮不发**：这类回答写的往往是
  「我觉得现在不太合适」这类犹豫说明，当正文发出去就是机器人当众自曝思考过程。
- 单次 LLM 调用有 90 秒超时，失败连续 3 次起指数退避并把原因写进日志。调用挂住
  不会把后台循环卡死。
- **日志不会刷屏**：持续故障（key 失效、平台掉线、磁盘满）时，同类日志按 5 分钟窗口
  聚合，只记第一条，末尾补一句「期间另有 N 次同类，已省略」。故障恢复后计数清零，
  下次再坏能立刻报出来。

### 拟人化特性

**时段与作息**：7 个时段的语气指导，加上按每个人自己的活跃小时画像挑时机。周末念头涨得快一些。

**能量影响**：读取 Humanoid Core 的精力与社交能量。累了不是「概率打折后照发」，而是念头根本攒不起来。

**显示「正在输入」**：她坐下来写这条主动消息的那几秒，QQ 会给对方显示「正在输入」——不是凭空亮一下，是真的在写的时候亮。做法与 Humanoid Core 那边同一套（照市场插件 `astrbot_plugin_input_state_by_nc`）：每 `input_state_interval_seconds` 秒报一次，只在 NapCat（aiocqhttp）私聊生效，其它平台自动跳过；关掉用 `input_state_enabled`。

**发送后的体验**：被接话会在意度上加分、冷落计数归零；没人理会降分、抬高下次门槛。回复率统计用 `reply_window_hours`，但「TA 是不是不想理我」的判定至少给半天 —— 晚上发的话对方早上才回，完全正常。

**不替她说话**：插件只提供**身体值**和**参考值**，不替 AI 写台词、不给它念稿子——
- **不给她现成的句子**。以前有 45 条固定例句（「刚想到一个事」「楼下的猫又在晒太阳」…）让她挑，
  结果每轮都在这几十句里轮着挑，看着像人，其实在背稿子。现在一条都没有。
- **不替她编经历**。以前有 80 条「她现在可能在想什么」（“楼下卖早餐的香味飘上来了”），
  相当于掷骰子决定她今天吃了什么、心情如何。现在动机由模型自己在生成前产生。
- **给素材，让她自己决定说什么**：现在几点、距上次跟 TA 说话多久、TA 最后说了什么、
  挂着什么事、她今天在干什么、外面天气——并明确告诉她「别编这里没有的事」。
- **给风格画像，不给句子**：从真实对话历史统计「TA 一条平均 7 个字、最长 11 字、
  基本不问句、习惯用句号收尾」。约束的是长度和结构，内容由模型造。

**对话记忆**：每人最近若干条对话（**包括她自己在主链路里说的话**）、话题关键词、时间锚点（「明天面试」）、没说结果的挂事（「今天面试了」）。prompt 里会单列「你自己上一句对TA说的是」。

**长期记忆联动（可选）**：装了「我会牢牢记住你」（`astrbot_plugin_memory_companion`）时，主动消息生成前会**按这次的由头**（为什么现在找这个人）去检索这个人的长期记忆、发完再把这条带上由头写回记忆库；一件还开着的事有了结果、或她许的诺兑现了，也会交棒写一条进去——惦记的事、上次没说完的，她记得住。开关 `memory_bridge_enabled`（默认开）；**没装就自动跳过**，主动消息照常发，只是没有这份记忆。桥接对象走 AstrBot 的插件注册表拿（不 importlib），不会因为插件重载认错。

**关系分级**：5 个关系档位决定能说什么、示例给到哪一档。

**消息类型**：6 种（分享想法、表达感受、延续话题、随口招呼、自然关心、时间反应）。

**反重复**：最近几次消息类型降权，并把最近发给对方的几条列进 prompt 要求换句式。

**连发模式**：主动消息可自然拆成 2-3 条短句，隔 1-3 分钟逐条补发；期间对方回话即停。上限由 `max_burst_parts` 控制。

### 指令

- `/自主社交状态` — 主人。看运行指标、各角色状态、念头面板、Core 联动、发送通道。
- `/社交自检` — 主人。**只结算、不调模型、不发消息**，几毫秒回答「链路通了吗、多少人
  念头够了」。装上之后不用干等一个心跳间隔。
- `/触发社交` — 主人。立刻挑一个最想说的人说一条。
- `/主动消息预览 [用户ID]` — 主人。**只生成、不发送**：看一眼她此刻打算对谁说什么，
  不影响由头、冷却与账本，用来调提示词。
- `/主动消息记录 [用户ID]` — 主人。最近 7 天发过什么，每条附一行**她为什么这时候发**。
- `/群社交状态` — 主人。在管的群、心流窗口、是否被隔离。

**用人格设定说话（按角色隔离，插件里没有人格配置项）**：主动消息直接取 AstrBot 内置人设，按目标会话解析。解析链与正常聊天一致，所以**多角色天然各用各的**。读不到人设时回退默认口吻，不阻塞发送。

**输出清洗**：markdown 符号、「消息：」标签前缀、泄进来的 `SEND` 协议标记、中文弯引号包裹、超长在句子边界截断（找不到边界就宁可略超长，不切在词中间）。

**不删括号动作**：`（轻轻为你披上薄毯）`、`*摸摸头*` 这类一律原样发出。语C 人设本来就靠它表达，删掉不是「更像真人」而是把角色抄平；无差别删除还会吃掉正常中文——「他去（上海）出差了」会变成「他去出差了」。换行也保留：QQ/微信里的聊天消息本来就是分行的。

**发出去之前有验收**。`SEND`/`NO` 协议只保证格式（首行是不是 SEND、有没有正文），
不保证内容——真实记录里 40 条「想表达…」这种描述说话的话、10 条括号残缺、
9 条只剩括号动作没正文，都是协议放过去直接发到手机上的。所以清洗之后、送出去之前
还有一道纯函数验收（零模型成本）：动机泄漏 / 括号残缺 / 只有动作没正文 / 复读 / 空泛。
**判不过就不发**（不重生成、不退回），念头保留、下一轮还能再试。
状态页和 `state.json` 的 `_runtime` 里能看到「累计拦下多少条、最近那条被拦的是什么」。

**用不用 emoji 不由配置决定，由她自己的说话习惯决定**：插件会统计她发出去的消息里带 emoji 的频率（会话历史 + 7 天主动消息日志），落成「爱用 / 偶尔 / 不用」三档，据此决定提示词怎么写、清洗时剥不剥；她自己样本不足时才看人设原文里带不带 emoji。所以爱用 emoji 的人格照旧发 ✨，一句一条 ❤️ 那种 AI 味则不会出现——它对应的其实是「她平时不用 emoji」这一档。

### 权限
`/触发社交` 与 `/自主社交状态` 默认**仅机器人主人**（AstrBot 全局配置 `admins_id`）可用。非主人在群里触发这些指令时插件**完全静默**——拒绝回复本身就会告诉所有群成员「这里有个能用的指令」。需要放开给别人，把 `owner_only_commands` 关掉并填 `allowed_trigger_uids`。`/自主社交状态` 的输出末尾会附上权限判定依据（你的 ID、主人列表、白名单），填错了照着这一行就能看出来。

### 性能
- Core 状态每个周期只读一次磁盘（按文件指纹缓存）。
- 观察消息标脏 + 周期刷盘；状态写入原子（tmp + replace）。
- 长期不活跃用户的历史正文、话题与作息画像自动清理（`user_retention_days`）。
- **状态文件读不出来时不会覆盖它**：先备份、再报错、并暂停写盘，等你修好文件重载插件。

### 兼容性
- 支持 `auto`、`standalone` 两种模式；与 Humanoid Core 只读衔接，不修改 Core 状态。
- 优先读 Core v2.14+ 的 `contract` 快照，读不到就按旧字段走。
- 主动消息依赖 `context.send_message`。qq_official 这类不支持主动发送的平台会发送失败，
  此时**不会**误记冷却与统计，也不会把用户隔离——那是平台的能力问题，不是这个人的问题。
- 社交状态按 bot 独立保存；状态文件自动补齐新字段。
- 兼容 AstrBot v4 新旧两套 API；引擎与状态层共用同一个可注入时间源。

## 配置项怎么理解

**80 个配置项，但真正需要动的通常只有 4 个**：

| 想达到的效果 | 调这个 |
|---|---|
| 整体更/更少主动说话 | `activity_level`（默认 75） |
| 两条消息之间至少隔多久 | `urge_refill_hours`（默认 4 小时） |
| 刚聊完多久内不另起话 | `recent_talk_minutes`（默认 18 分钟） |
| 晚上几点到几点不说话 | `quiet_start` / `quiet_end`（默认 23–7） |

其余项基本都有合理默认值，动之前先读下面的说明。

> **一个必须知道的精度问题**：插件是按「心跳」醒来的，默认每 8–15 分钟看一眼。
> 所以 `probe_after_minutes`（默认 12 分钟）这类分钟级配置，**实际最快也要等一个心跳**
> 才可能触发——把它从 12 调到 13，在默认心跳下不会有任何区别。想让分钟级配置真正按
> 分钟生效，把 `heartbeat_min_minutes` 调到 1。心跳变快**不会**让你多发消息
> （发不发仍由念头与冷却决定），只是让「到点了」被发现的时机更准。

> **升级后节奏没变**：AstrBot 不会覆盖你已有的配置。插件**不会**偷偷改你的设置——
> 启动时只在日志里告诉你哪些项还停在旧版本的默认值上，要不要跟新版节奏由你在面板里决定。

## 升级（覆盖安装）
AstrBot 的「本地安装 zip」不会覆盖同名目录：装过旧版时直接上传会报
`安装失败：目录 astrbot_plugin_autonomous_social 已存在。`，插件列表里的「更新」也只会报
`该插件不是通过插件市场安装，无法检测或执行更新。`（上传安装的插件没有市场来源）。
所以升级二选一，两种都不丢状态与配置：

1. 面板：插件 → 本插件 → 卸载（**不要勾**「删除配置」「删除数据」）→ 立即上传新 zip。
   配置在 `data/config/<目录名>_config.json`、状态在 `data/plugin_data/<目录名>/`，
   卸载只删 `data/plugins/<目录名>` 这一个目录，两个都不动。
2. 终端原地替换：先把新 zip 用「本地安装」上传一次（会失败，但包已落到
   `data/temp/plugin_upload_<原文件名>`），再解压覆盖 `data/plugins/<目录名>`，最后在面板点「重载」。

上传失败后如果 `data/plugins/` 里留下 `plugin_upload_*` 之类的残留目录，或插件出现在
「加载失败的插件」列表里，要先把它删掉/卸载，否则下次上传仍会撞「目录已存在」。

## 数据
- `data/plugin_data/astrbot_plugin_autonomous_social/state.json`：本插件自己的状态。
- `data/plugin_data/astrbot_plugin_autonomous_social/humanoid_signals.json`：写回给
  Humanoid Core 的信号（Core 只读，超过 15 分钟不采信）。
- `data/plugin_data/astrbot_plugin_autonomous_social/config_baseline.json`：
  「旧默认值提示只说一次」的标记。

> **状态文件读不出来时**（损坏、非 UTF-8、结构不对）：插件会把原文件重命名成
> `state.json.unreadable.<时间戳>` 备份、记一条 error 日志，并**暂停写盘**，
> 不会拿空状态盖掉它。修好文件后重载插件即可恢复。

## 指令
- `/自主社交状态`：念头面板（谁攒到多少、多久没说话、上次是被接住还是没接）、当前节奏参数、Core 与人格联动、**当前读到了哪一层、哪些能力因读不到 Core 而停用**、LLM 退避状态、权限判定依据。仅主人/白名单。
- `/触发社交`：立刻挑念头最重的人说一句，绕过念头门槛与冷却，也不经过模型否决（主人要看效果就别替他否决），但仍不插话进热聊。**多台 bot 同群时，群里触发要 @ 本 bot（`trigger_group_requires_at`）**，否则群里一条命令会把所有装了本插件的 bot 一起叫醒。
  触发前会先验三件事——引擎在跑吗、插件启用了吗、模型是不是正在失败退避中——任何一条不满足都直接拒绝并说明原因，不动任何状态。
  万一第一个候选人发不出去（模型抖一下、平台断一下），会自动换下一个，最多试 3 个；全失败时汇总每一位的原因。仅主人/白名单。
- `/主动消息记录 [用户ID]`：看最近 7 天发过的主动消息（按用户隔离不串台）。仅主人。
- `/群社交状态`：群聊心流在管的群列表——最近活跃、心流窗口是否开着、是否被隔离（被踢/会话失效）。仅主人。
